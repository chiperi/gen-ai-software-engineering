## 3. Findings

### SEC-001 — Текст помилки читання файлу розкриває абсолютний шлях ФС

- **Рівень**: MEDIUM
- **Категорія**: розкриття інформації (CWE-209, CWE-200)
- **Місце**: `src/coupons.js:14`, шлях назовні — `src/server.js:35`
  **[суміжний контекст]**

```js
// src/coupons.js:14
  return JSON.parse(fs.readFileSync(file, 'utf8'));
```
```js
// src/server.js:35
      return send(res, 400, { error: err.message });
```

**Ризик.** Валідація на рядку 10 відсіює неправильний *формат* коду, але
нічого не робить із кодом правильного формату, для якого файлу не існує.
`fs.readFileSync` кидає `ENOENT`, чий `err.message` містить **повний
абсолютний шлях**. `src/server.js:35` віддає `err.message` клієнту дослівно.
Те саме стосується `JSON.parse` для пошкодженого файлу купона — повідомлення
містить фрагмент вмісту файлу та зміщення.

**Сценарій експлуатації.** Неавтентифікований запит
`GET /coupon?code=ZZZZZZ` → відповідь `400` з тілом
`{"error":"ENOENT: no such file or directory, open
'/Users/<user>/Projects/.../homework-4/data/ZZZZZZ.json'"}`.
Атакувальник безкоштовно отримує: ім'я користувача ОС, повний шлях
розгортання, назву каталогу даних. Це прямий вхід для наступних атак
(підбір шляхів логів, локальні включення, соціальна інженерія). Додатково
різниця відповідей `200` vs `400/ENOENT` дає оракул перебору: перебором
`^[A-Z0-9]{3,16}$` можна встановити повний перелік наявних купонів, зокрема
неопублікованих промокодів.

**Рекомендація.** Обгорнути читання й розбір файлу так, щоб назовні йшло
лише узагальнене повідомлення без деталей ФС, а оригінальна помилка
залишалась у серверному лозі. Відсутній купон і невалідний код мають давати
**однакову** відповідь клієнту, щоб прибрати оракул перебору. Окремо —
`src/server.js:35` не повинен транслювати `err.message` довільної помилки:
клієнту слід віддавати лише повідомлення явно дозволених типів помилок.

### SEC-002 — `calculateTotal` не валідує елементи кошика

- **Рівень**: MEDIUM
- **Категорія**: відсутня валідація (CWE-20), цілісність бізнес-логіки
- **Місце**: `src/cart.js:6-10` (тіло, змінене в Change 1)

```js
// src/cart.js:6-10
    let total = 0;
    for (const item of items) {
        total += item.price * item.quantity;
    }
    return total;
```

**Ризик.** Перевірка на рядку 2 гарантує лише те, що `items` — масив. Вміст
елементів не перевіряється ніяк: ні тип, ні знак, ні скінченність, ні
наявність полів. Change 1 **збільшив** вагу цієї прогалини: до правки
множник був відсутній і зловмисник керував лише `price`, тепер він керує
добутком двох неперевірених полів. Дані потрапляють сюди прямо з тіла
HTTP-запиту (`src/server.js:41-42`) без жодної проміжної перевірки.

**Сценарій експлуатації.** Неавтентифікований
`POST /checkout` з тілом `{"items":[{"price":-1000,"quantity":1}]}` →
`{"total":-1000}`. Від'ємна сума проходить далі: `applyDiscount(-1000, 0)`
повертає `-1000`, сервіс відповідає `200`. Варіанти того самого входу:
`{"price":"10","quantity":"3"}` → `30` (неявне приведення рядків);
`{"price":1e308,"quantity":10}` → `Infinity`, після чого
`JSON.stringify(Infinity)` дає `{"total":null}`;
`{"items":[{}]}` → `NaN` → також `{"total":null}`;
`{"items":[null]}` → `TypeError`, чий текст (`Cannot read properties of null
(reading 'price')`) віддається клієнту через `src/server.js:45-47`. У
будь-якому конвеєрі, де `total` веде до оплати чи нарахування балансу,
від'ємна сума — це кредит на користь атакувальника.

**Рекомендація.** Перевіряти кожен елемент перед використанням: що це
об'єкт; що `price` і `quantity` — скінченні числа (`Number.isFinite`), а не
рядки, що приводяться; що обидва невід'ємні; що `quantity` ціле; що є
верхня межа на кількість позицій у кошику й на значення полів. Перевірку
розмістити всередині `calculateTotal`, а не лише в обробнику HTTP — тоді
вона покриє всі майбутні шляхи виклику, за тим самим принципом, що вже
застосовано в `loadCoupon`.

### SEC-003 — Тіло запиту накопичується без обмеження розміру

- **Рівень**: MEDIUM
- **Категорія**: відсутня валідація (довжина вводу), доступність (CWE-770)
- **Місце**: `src/server.js:12-25` **[суміжний контекст]**

```js
// src/server.js:14-16
    let raw = '';
    req.on('data', (chunk) => { raw += chunk; });
    req.on('end', () => {
```

**Ризик.** Це канал доставки для SEC-002: сюди надходить масив `items`, який
далі обробляє змінена функція. Обмеження на розмір тіла немає — рядок
`raw` росте, поки клієнт надсилає дані. Немає ні ліміту байтів, ні тайм-ауту,
ні обмеження кількості елементів у розібраному масиві.

**Сценарій експлуатації.** Неавтентифікований клієнт відкриває
`POST /checkout` і повільно надсилає кілька гігабайт тіла. Пам'ять
одного-єдиного процесу Node зростає до OOM-kill; сервіс недоступний для
всіх. Дешевший варіант: одне тіло з масивом на мільйони елементів —
`JSON.parse` плюс цикл `calculateTotal` займають event loop, і всі інші
запити стоять.

**Рекомендація.** Ввести жорсткий ліміт на сумарний розмір тіла з негайним
розривом з'єднання при перевищенні, тайм-аут на читання, а також окрему
верхню межу на довжину масиву `items` уже після розбору. Це суміжний файл
поза `FILES_CHANGED` — виправлення варто планувати окремою задачею, а не
дописувати до цієї правки.

### SEC-004 — Підсумковий шлях не перевіряється після побудови

- **Рівень**: LOW
- **Категорія**: обхід шляху (залишковий ризик, CWE-59)
- **Місце**: `src/coupons.js:13`

```js
// src/coupons.js:13
  const file = path.join(DATA_DIR, `${code}.json`);
```

**Ризик.** Allow-list на рядку 10 робить вихід за межі `data/` **через саму
назву** неможливим — у `code` не може бути ні `/`, ні `\`, ні `.`, ні
NUL-байта. Проте контроль побудований лише на вхідному рядку: результат
`path.join` не звіряється з `DATA_DIR` і не резолвиться до реального шляху.
Отже, будь-який спосіб вийти за межі каталогу *поза* назвою залишається
неперекритим.

**Сценарій експлуатації.** Потрібен запис у `data/` (скомпрометований
процес деплою, розпакування архіву, спільний том контейнера). Атакувальник
створює символьне посилання `data/ABCDEF.json → ../credentials.json`
(або на будь-який файл поза проєктом). Запит `GET /coupon?code=ABCDEF`
проходить регулярний вираз, `readFileSync` іде за посиланням і повертає
чужий вміст із кодом `200`. Тобто саме той наслідок, який закривав
`VULN-001`, але іншим шляхом. Рівень LOW через попередню умову: без права
запису в `data/` сценарій недосяжний.

**Рекомендація.** Після побудови шляху резолвити його до канонічного
(з розкриттям символьних посилань) і перевіряти, що результат лежить
усередині канонічного `DATA_DIR`; за потреби — відмовлятись читати
не-звичайні файли. Це другий, незалежний від назви рубіж контролю: allow-list
на вході, перевірка підсумкового шляху на виході.

### SEC-005 — `applyDiscount` валідує `percent`, але не `subtotal`

- **Рівень**: LOW
- **Категорія**: відсутня валідація (CWE-20)
- **Місце**: `src/cart.js:13-17` (функція, змінена в Change 2)

```js
// src/cart.js:13-17
export function applyDiscount(subtotal, percent) {
    if (typeof percent !== 'number' || Number.isNaN(percent) || percent < 0 || percent > 100) {
        throw new RangeError('percent must be between 0 and 100');
    }
    return subtotal * (1 - percent / 100);
}
```

**Ризик.** Валідація `percent` повна й коректна (див. розділ 4). Але другий
параметр, `subtotal`, не перевіряється взагалі — і саме він приходить із
неперевіреного кошика. Класична асиметрія: наявність перевірки в функції
створює хибне враження, що функція валідована цілком.

**Сценарій експлуатації.** `POST /checkout` з
`{"items":[{"price":1e308,"quantity":10}],"coupon":"SAVE10"}` →
`subtotal` = `Infinity` → `Infinity * 0.9` = `Infinity` →
`JSON.stringify` перетворює це на `{"total":null}`, і клієнт отримує `200 OK`
з `null` замість помилки. Те саме для `{"items":[{}]}` → `NaN` → `null`.
Прямої вигоди для атакувальника немає — звідси LOW; ризик у тому, що
відповідь `200` з `null` мовчки проходить далі по конвеєру замість того,
щоб зупинитись помилкою.

**Рекомендація.** Симетрично до перевірки `percent` вимагати, щоб `subtotal`
був скінченним невід'ємним числом, і кидати помилку інакше. Додатково —
на рівні `src/server.js` не віддавати `200`, якщо обчислений результат не є
скінченним числом.

### SEC-007 — Сервіс без автентифікації, обмеження частоти й захисних заголовків [INFO]

- **Рівень**: INFO
- **Категорія**: веб-специфічне
- **Місце**: `src/server.js:27-51` **[суміжний контекст]**

**Спостереження.** Обидва маршрути (`GET /coupon`, `POST /checkout`) відкриті
без автентифікації та без обмеження частоти запитів — саме тому решта
знахідок цього звіту досяжні неавтентифіковано, і саме тому оракул перебору
з SEC-001 практично реалізовний. Заголовків `X-Content-Type-Options`,
`Cache-Control` у відповідях немає.

За окремими веб-ризиками: **XSS** — відповіді формуються лише через
`JSON.stringify` із явним `Content-Type: application/json`
(`src/server.js:8`), HTML не генерується, вразливості немає. **CORS** —
заголовків `Access-Control-Allow-*` не встановлено, тож діє звичайна
заборона браузера; вразливості немає. **CSRF** — маршрути не змінюють стан і
не використовують cookie чи сесії, тож класичний CSRF незастосовний.
**Забруднення прототипу** — розібраний JSON ніде не зливається з іншими
об'єктами (`Object.assign`/spread/merge відсутні), доступ лише через
деструктуризацію `src/server.js:41`; вразливості немає.

**Рекомендація.** Для навчального сервісу змін не потрібно. Перед будь-яким
розгортанням поза localhost — автентифікація на обох маршрутах, обмеження
частоти (зокрема на `/coupon` через оракул перебору) і `nosniff` у відповідях.

### VULN-001 — обхід каталогу в `loadCoupon` → **FIXED**

Виправлення (`src/coupons.js:7`, `9-12`):

```js
// src/coupons.js:7
const COUPON_CODE = /^[A-Z0-9]{3,16}$/;
```
```js
// src/coupons.js:9-12
export function loadCoupon(code) {
  if (typeof code !== 'string' || !COUPON_CODE.test(code)) {
    throw new Error('invalid coupon code');
  }
```

**Питання 1 — чи це allow-list?** **Так.** Це не заборона `..`, а дозвіл
рівно `A-Z0-9`. Перевірено на обхід:

| Спроба обходу | Результат | Чому |
|---|---|---|
| `../credentials` | відхилено | `.` і `/` поза класом символів |
| `%2e%2e%2fcredentials` | відхилено | `searchParams.get` декодує **до** перевірки; регулярний вираз бачить `../` |
| `..%252fcredentials` | відхилено | після одного декодування лишається `%`, не в класі |
| `SAVE10/../../etc/passwd` | відхилено | `/` поза класом |
| `SAVE10\..\..\x` (Windows) | відхилено | `\` поза класом |
| `SAVE10\n../credentials` | відхилено | у JS без прапорця `m` `$` збігається лише з кінцем рядка і **не** перед завершальним `\n` (на відміну від Python) |
| `SAVE10\0../x` | відхилено | NUL поза класом |
| повноширинні/Unicode-омогліфи `ＳＡＶＥ１０` | відхилено | клас лише ASCII |
| `save10` (нижній регістр) | відхилено | клас лише верхній регістр |
| `AB` / рядок на 17+ символів | відхилено | межі `{3,16}` |
| `null`, `undefined`, `["../x"]`, `{toString}` | відхилено | `typeof code !== 'string'` спрацьовує **першим** — до `.test()`, тож приведення об'єкта до рядка не відбувається |

Вираз анкерований з обох боків (`^`…`$`), без прапорців `g`/`m`/`i` —
отже, немає ні проблеми зі станом `lastIndex` при повторних викликах, ні
багаторядкового послаблення, ні регістронезалежності. ReDoS неможливий:
жодного вкладеного квантифікатора, довжина обмежена `{3,16}`.

**Питання 2 — чи повне покриття входів?** **Так.** Перевірено пошуком по
всьому дереву `**/*.js` за `readFile|createReadStream|path.join|exec|eval|
require(`: єдина операція читання файлу в кодовій базі — `src/coupons.js:14`,
єдина побудова шляху з вводу — `src/coupons.js:13`, обидві всередині
`loadCoupon`. Шляхів виклику `loadCoupon` рівно два — `src/server.js:33`
(рядок запиту `?code=`) і `src/server.js:43` (поле тіла `coupon`) — і обидва
проходять через ту саму перевірку, бо її розміщено **всередині функції**,
а не в обробнику HTTP. Це правильне місце: новий шлях виклику успадкує
перевірку автоматично. Застереження: другий шлях підтверджено читанням коду,
але не запуском — див. SEC-008.

**Питання 3 — чи не з'явився новий ризик?** **Сам фікс — ні.** Текст
`'invalid coupon code'` — константний рядок, не містить ні вхідного значення
(немає ризику відображеного вводу), ні шляху ФС. Тип `Error` коректно
відображається обробником у `400`. Але правка **не усунула** сусідній канал
розкриття: для коду правильного формату помилка `ENOENT` від
`readFileSync` досі йде клієнту з абсолютним шляхом — див. **SEC-001**. Це
дефект, що існував до правки; фікс не привніс його, але й звузив лише
вхідний бік. Другий залишковий ризик — відсутність перевірки підсумкового
шляху (**SEC-004**), який allow-list за назвою принципово не покриває.

**Висновок.** Обхід каталогу через користувацький ввід закрито повністю:
жоден вхід не дозволяє вийти за межі `data/`. `VULN_001_STATUS: FIXED`.
SEC-001 і SEC-004 — залишкові ризики суміжного характеру, не регресія
`VULN-001`.

### BUG-002 — валідація `percent` у `applyDiscount` (побічна перевірка безпеки)

Change 2 додав перевірку діапазону, тож вона теж проходить три питання.

**Питання 1 — allow-list?** **Так**, за суттю: `typeof percent !== 'number'`
пропускає лише числа, далі відсікаються `NaN` і все поза `0..100`.
Перевірено крайні входи: `Infinity` (`> 100` → відхилено), `-Infinity`
(`< 0` → відхилено), `NaN` (`Number.isNaN` → відхилено), `"10"` (рядок →
відхилено, немає приведення), `null`/`undefined` (не `number` → відхилено),
`new Number(10)` (об'єкт → відхилено), `-0` (проходить, результат
коректний). Прогалин не знайдено.

**Питання 2 — повне покриття?** Для `percent` — так, перевірка всередині
функції, обидва джерела значення (`0` за замовчуванням і `loadCoupon(...).percent`
з `src/server.js:43`) її проходять. Купон із нечисловим `percent` у JSON дасть
`RangeError` → `400`, а не мовчазне сміття. Для **другого параметра,
`subtotal`, покриття нульове** — див. SEC-005.

**Питання 3 — новий ризик?** Текст `'percent must be between 0 and 100'`
не містить вхідного значення й не розкриває нічого про систему. Нового
ризику фікс не вносить.

### BUG-001 — множення на `quantity` в `calculateTotal`

Не є виправленням безпеки, але змінює обробку неперевіреного вводу, тому
перевірено за тими самими питаннями. Allow-list на вміст елементів **відсутній**
(`Array.isArray` перевіряє лише контейнер), покриття входів **неповне**,
і правка **розширила** керовану атакувальником поверхню з одного поля
(`price`) до двох (`price × quantity`) — див. **SEC-002**.
